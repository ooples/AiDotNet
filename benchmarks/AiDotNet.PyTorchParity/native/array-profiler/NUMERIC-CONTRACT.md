The new `ArrayProfilerSnapshotV2` is a separate diagnostic ABI. The existing `ArrayProfilerSnapshot` export, its exact seven-slot layout, legacy phase fields and shutdown `snapshot` remain intact. V2 copies that prefix and the extended counters in one lock; it has version 2 and 1,370 unsigned 64-bit slots. The build receipt hashes `NumericArrayCounters.h` as well as the original source and records both lengths. No performance acceptance policy switches automatically to V2.

Slots 9–12 report primitive candidate count, successfully classified primitive count, exact successful payload bytes and full primitive-object bytes. Slots 13–17 report payload metadata/rank/overflow/size failures and their conservative full-object bytes. Slots 18–23 separate known reference arrays, unsupported element types and unknown classes. Slots 24/25 flag counter overflow and non-exact object-size results. Slots 26 onward contain `(count,payload bytes,full-object bytes)` by dtype then rank 1–32. Dtype order is `bool,char,i1,u1,i2,u2,i4,u4,i8,u8,r4,r8,native_i,native_u`.

`IsArrayClass` establishes primitive element type and rank; `GetArrayObjectInfo` supplies dimensions, including multidimensional arrays and empty arrays. The callback uses fixed stack metadata, does not inspect or retain a payload pointer, and makes all CLR queries before acquiring the counter lock. Checked multiplication validates payload size against the full object size. Unknown classes and unsupported value types (including Half, Decimal, Complex, enums and arbitrary structs) remain explicit full-object candidates. A failed payload query retains the successfully measured full object as its upper bound. A failed size query, counter overflow or inconsistent receipt invalidates even that bound. Reference-element generic tensor storage requires a separate actual-dtype audit or the original all-array upper bound; this provider does not certify that arbitrary reference-element arrays cannot be numeric storage.

These counters measure fresh array payloads and full object sizes observed at CLR allocation callbacks. Full object size includes object headers but does not establish GC alignment padding, heap reservation, unmanaged allocations or physical RAM. Pool hits and arena borrows create no fresh arrays. Framework requested-storage accounting must add audited successful borrow request bytes/counts separately; a cold rent may be conservatively double counted. Backing-acquisition accounting must keep those borrowed requests separate and include independently audited framework native workspace acquisitions. Vendor-internal bypasses may be symmetrically excluded by the measurement contract; framework-owned vendor workspaces remain included. Whole-process RAM/VRAM peaks are separate required measurements.

Before any model use, run the original `smoke/ArrayProfilerSmoke.csproj` unchanged, then `numeric-smoke/NumericArrayProfilerSmoke.csproj --contracts` without the profiler, and `--native` in a new launch-enabled profiler process. The new smoke checks all fourteen primitive widths, a zero-length array, rank-two payload, reference/unsupported separation, conservative failure receipts and a warmed pool borrow. No source-only preparation is a passing runtime receipt. Check the matching-PID complete shutdown, source/build/DLL hashes, zero size/overflow failures, and bin reconciliation. Use fresh outputs; preserve failures.

The strongest prospective CPU comparison is an audited Ai upper bound versus a Torch lower bound: Ai fresh candidate payloads/count plus audited pool/arena requests and framework native requests, compared with positive CPU allocator events in matching fixed phase windows and the actual launched PID. Torch event coverage must be controlled with known CPU tensor fresh allocations, views and reuse; events alone do not prove every provider is covered. Unsupported/unknown Ai objects can enlarge its bound, never reduce it. For backing API acquisition comparisons, use the full-object candidate bound plus covered native acquisitions and compare only a proven compatible Torch allocator-event lower bound. Do not describe this as malloc or physical heap traffic.

For CUDA, native caching-allocator requested counters and segment-acquisition counters measure different things. Verify the actual allocator backend before interpreting its fields; unsupported statistics (for example a backend that does not implement them), counter resets, missing provider events or foreign PID/phase data fail closed. Control fresh tensor, alias/view, freed/reused tensor and known workspace cases under the actual configured allocator. Ai successful compiled/step-pool loans belong to requested accounting, while device backend acquisitions belong to backing accounting. Do not add logical loans to physical acquisitions or infer peak memory reductions from released logical storage.
